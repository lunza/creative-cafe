# 对话/写作/世界书三模式智能体化升级分析 Spec

## Why

用户反馈：当前 AI"智能体的作用还是太低"。代码盘点证实——尽管项目已具备丰富的 AI 能力，但 AI 始终是**"用户操作的工具"**而非**"自驱的智能体"**：

- **对话模式**：AI 仅在回复用户消息时被动生成，已有 `<tableEdit>` 文本协议（[tableEditParser.ts](file:///g:/AI/creative-cafe/src/main/services/memory/tableEditParser.ts)）可让 AI 编辑状态表，但无主动检索、无工具调用循环。
- **写作模式**：已有 [AIAssistedChapterService](file:///g:/AI/creative-cafe/src/main/services/writing/AIAssistedChapterService.ts)、[OutlineGenerator](file:///g:/AI/creative-cafe/src/main/services/writing/OutlineGenerator.ts)、[PlotCheckerService](file:///g:/AI/creative-cafe/src/main/services/writing/PlotCheckerService.ts)（5 维审核+逻辑矛盾+autoFix）、[DescriptionPolisher](file:///g:/AI/creative-cafe/src/main/services/writing/DescriptionPolisher.ts) 等，但每个都是**用户点击触发的一次性调用**，无"读大纲→写章→自审→修复→更新表格→下一章"的自驱闭环。
- **世界书模式**：[useWorldBookAIOperations.ts](file:///g:/AI/creative-cafe/src/renderer/components/WorldBook/hooks/useWorldBookAIOperations.ts) 已含 15+ AI 操作（翻译/润色/生成关键词/生成条目/从角色生成/模板生成/排序），但**全部用户手动触发**，AI 不会在对话/写作中自主扩展世界书。

**最大未开发机会**：`supportsToolCalling` 能力已检测但**全项目未使用**（仅 [storageService.ts:234](file:///g:/AI/creative-cafe/src/main/services/storageService.ts) `use_function_calling: false` 占位）。引入原生工具调用 + 智能体循环（agent loop），可将三模式从"被动工具"升级为"自驱智能体"。

本 Spec 为**分析型/路线图型文档**，认真梳理三模式现状，提出智能体化升级与开发建议，每个方向详述实现方案、能力组合、预期收益、技术挑战，作为后续独立 Spec 立项依据。

## What Changes

本 Spec 不直接产出代码，产出物为：

- 三模式（对话/写作/世界书）现状的代码级盘点
- 共享的「工具调用智能体引擎」基础设施设计
- 三个智能体化升级方向（每方向四要素）
- 三维评估矩阵与优先级建议
- 后续独立 Spec 立项清单

| # | 方向 | 核心能力组合 | 落地点 |
|---|------|-------------|--------|
| 0 | 工具调用智能体引擎（三模式共享基础设施） | 工具调用 + 文本 | `src/main/services/ai/agent/`（新增） |
| A | 对话角色卡 → 自驱智能体（自主表格整理 + 主动检索） | 工具调用 + 文本（+视觉可选） | ChatEngine / PromptBuilder |
| B | 写作模式 → 写作智能体（自驱创作 + 剧情审核 + 表格整理闭环） | 工具调用 + 文本 | AIAssistedChapterService / PlotCheckerService / TableOrganizeService |
| C | 世界书 → AI 自驱编写（自主扩展 + 自主维护 + 主动注入） | 工具调用 + 文本 | worldBookService / useWorldBookAIOperations |

## 现状盘点（代码级）

### 一、对话模式现状

| 组件 | 文件 | 现状 |
|------|------|------|
| 聊天引擎 | `src/renderer/components/Common/ChatEngine/ChatEngine.ts` | 调用 `AIService.streamChatAPI` 流式生成回复 |
| 提示词构建 | `src/renderer/components/Character/CharacterDialogueChat/PromptBuilder.ts` | 拼装角色卡字段 + `buildAsyncTableOrganizeInstructions`（注入 `<tableEdit>` 协议说明） |
| 表格编辑协议 | `src/main/services/memory/tableEditParser.ts` | 解析 AI 回复中的 `insertRow/updateRow/deleteRow`，应用到状态表 |
| 世界书注入 | `src/main/services/WorldBookKeywordMatcher.ts` | **被动**关键词匹配 + scan_depth/token_budget/recursive_scanning |
| 向量检索 | `src/main/services/ChatVectorizationService.ts` | 已有向量化历史对话能力，但未被对话流程主动调用 |

**当前自主性**：AI 仅在"回复用户消息时"被动生成；表格编辑是 fire-and-forget（AI 输出命令，无法看到执行结果再决策）；世界书靠关键词撞运气注入；**无工具调用循环**。

### 二、写作模式现状

| 组件 | 文件 | 能力 |
|------|------|------|
| 章节拆分/合并 | `AIAssistedChapterService.ts` | AI 拆分长章 / 合并短章 |
| 大纲生成 | `OutlineGenerator.ts` | AI 生成/扩展大纲 |
| 剧情审核 | `PlotCheckerService.ts` | 5 维审核（大纲一致/世界书合规/角色一致/写作风格/剧情连续）+ 逻辑矛盾检测 + autoFix + quickFix |
| 描述润色 | `DescriptionPolisher.ts` | AI 润色文本 |
| 风格学习 | `WritingStyleLearningService.ts` | 学习用户写作风格 |
| 表格组织 | `TableOrganizeService.ts` + `TableOrganizeMainPanel.tsx` | 章节/大纲/角色/情节表格管理 |
| 章节类型 | `src/shared/types/writing.types.ts` | Chapter/Outline/CharacterCard/WritingProject 完整数据模型 |

**当前自主性**：每个服务都是**用户点击触发的一次性调用**；章节生成不会自动触发剧情审核；剧情审核发现的问题不会自动修复后重新审核；表格不会随章节生成自动更新；**无自驱写作循环**。

### 三、世界书模式现状

| 组件 | 文件 | 能力 |
|------|------|------|
| CRUD | `worldBookService.ts` | 条目增删改查，字段含 id/name/content/keywords/position/enabled/**autoGenerated** |
| 关键词匹配 | `WorldBookKeywordMatcher.ts` | 被动注入 |
| 向量检索 | `ChatVectorizationService.ts` + `EmbeddingService.ts` | 语义检索已具备 |
| AI 操作 | `useWorldBookAIOperations.ts` | **15+ 操作**：translateText/polishText/generateKeywords/generateTagsForEntry/handleGenerateNewEntries/handleGenerateEntries/handleTemplateGenerateEntries/handleAISortEntries/handleGenerateFromCharacters/handleCreateFromAI/handleCreateWorldBook 等 |
| IPC | `src/main/ipc/handlers/worldBookHandlers.ts` | CRUD + AI 操作通道 |

**当前自主性**：AI 操作**全部用户手动触发**；对话/写作过程中 AI 不会自主发现"这里提到一个新地点/角色"并自动创建世界书条目；条目不会自主动态排序/去重/合并；**无自驱扩展**。

### 三模式共性缺口

1. **工具调用能力零使用**——`supportsToolCalling` 检测了但没用
2. **无智能体循环**——AI 不能"调用工具→看结果→再决策"
3. **`<tableEdit>` 是 fire-and-forget**——AI 输出命令后无法获知执行结果
4. **所有 AI 操作是用户触发的一次性调用**——无自驱工作流

## 方向 0：工具调用智能体引擎（三模式共享基础设施）

### 功能概述
新增一套统一的工具调用引擎，封装 OpenAI 兼容的 function-calling 协议，提供「工具注册 + 请求构建 + tool_calls 执行 + 结果回填 + 循环控制 + 降级」能力，作为三模式智能体化的共享底座。现有 `<tableEdit>` 文本协议可逐步迁移为原生工具调用（更可靠、可闭环）。

### 1) 具体实现方案
- **新增目录** `src/main/services/ai/agent/`：
  - `toolRegistry.ts`：工具注册中心，每个工具声明 `{name, description, parameters(JSONSchema), handler}`，支持按模式（对话/写作/世界书）分组启用
  - `agentLoop.ts`：核心循环——发送含 `tools` 的请求 → 若响应含 `tool_calls` → 并行执行 handler → 将结果以 `role:'tool'` 消息追加 → 重新发送 → 直至模型返回最终文本（`maxIterations=8` 防死循环）
  - `toolProtocolAdapter.ts`：兼容不同厂商协议差异（`tool_calls` vs 旧 `function_call`、`parallel_tool_calls`、`response_format`）
  - `agentTypes.ts`：`AgentTool`、`AgentTurn`、`ToolCallEvent` 等类型
- **AIService 扩展**：新增 `streamChatWithTools(messages, tools, callbacks)`，在现有 `streamChatAPI` 基础上增加 tools 参数与循环；流式输出最终文本，工具调用过程通过 `onToolCall` 事件推送前端
- **工具实现**（按模式分组）：
  - **对话组**：`searchWorldbook(query)`、`searchChatHistory(query)`（复用 ChatVectorizationService）、`getCharacterState()`、`updateStateTable(commands)`（原生工具版的 tableEdit，返回执行结果）、`addMemoryNote(key, value)`
  - **写作组**：`readOutline()`、`writeChapter(index, content)`、`checkPlot(chapterIndex)`（复用 PlotCheckerService）、`applyAutoFix(issueId)`、`updateWritingTable(commands)`、`polishText(text)`、`generateNextChapter()`
  - **世界书组**：`searchEntries(query)`、`createEntry(entry)`、`updateEntry(uid, patch)`、`mergeEntries(uids)`、`generateKeywords(content)`、`expandFromContext(contextText)`
- **降级策略**：`supportsToolCalling=false` 时回退到现有 `<tableEdit>` 文本协议 + 关键词匹配路径，完全不影响现有体验
- **可观测性**：工具调用过程通过 IPC `ai:agentToolCall` 事件推送，前端可折叠展示"AI 调用了：searchWorldbook(2条) / updateStateTable(1行)"

### 2) 所需调用的模型能力组合
- **工具调用（必须）**：发起 function call 并消费结果
- **文本生成（必须）**：基于工具结果生成最终输出
- 组合：`supportsToolCalling && supportsText` → 工具调用 + 文本

### 3) 预期提升的用户体验或业务指标
- **基础设施价值**：一次建设，三模式复用；为后续所有智能体功能提供统一底座
- **可靠性**：原生工具调用比 `<tableEdit>` 文本解析更可靠（无正则解析失败）；可闭环（AI 看到执行结果）
- **业务指标**：解锁方向 A/B/C 的全部收益

### 4) 技术挑战及解决方案
| 挑战 | 解决方案 |
|------|---------|
| 厂商工具调用协议差异大（OpenAI/Anthropic/国产） | `toolProtocolAdapter` 适配层，按 engine 类型分发；先支持 OpenAI 兼容协议（项目主流） |
| 循环延迟（多轮往返） | 工具并行执行；首 token 延迟 +1~3s 可接受；UI 显示"正在思考/检索…" |
| 死循环/重复调用同一工具 | `maxIterations=8` 硬上限；同工具+同参数去重缓存（缓存命中直接返回上次结果） |
| 工具 handler 抛错导致整个循环崩溃 | 每个 handler try-catch，失败返回 `{error: '...'}` 给模型，让模型自行降级 |
| 现有 `<tableEdit>` 文本协议迁移风险 | 双轨并行：新工具调用优先，文本协议作为降级兜底；不一次性删除旧解析器 |
| 工具 schema 设计不当（模型不调或乱调） | 严格 JSONSchema + system prompt 明确"何时调用"；先小范围 A/B 调优 |

## 方向 A：对话角色卡 → 自驱智能体

### 功能概述
将对话中的角色卡从"被动回复器"升级为"自驱智能体"：AI 在对话过程中可主动调用工具检索世界书/历史、自主整理状态表（关系/库存/剧情进度）、主动记忆关键事件，并在适当时机主动发起行动（而非仅回应用户）。`<tableEdit>` 升级为原生 `updateStateTable` 工具，AI 能看到执行结果并据此调整后续行为。

### 1) 具体实现方案
- **工具集**（启用对话组）：
  - `searchWorldbook(query)` — 替代被动关键词匹配，AI 主动按需检索
  - `searchChatHistory(query)` — 复用 ChatVectorizationService，长会话不失忆
  - `getCharacterState()` — 读取当前关系/库存/剧情表
  - `updateStateTable(commands)` — 原生工具版 tableEdit，**返回执行结果**（成功/失败/新状态），AI 可闭环
  - `addMemoryNote(key, value)` — AI 主动记录长期记忆条目
- **PromptBuilder 改造**：`buildAsyncTableOrganizeInstructions` 从"教 AI 输出 `<tableEdit>` 文本"改为"告知 AI 可用工具及调用时机"；保留文本协议作为降级
- **ChatEngine 集成**：发送消息时改用 `streamChatWithTools`，传入对话组工具集；`onToolCall` 事件驱动前端"AI 正在检索/整理…"loading 动画
- **主动行动能力**（高阶，二期）：允许 AI 在工具调用后判定"需要主动推进剧情"，生成主动行动消息（如角色主动找上门），需用户在设置中开启"主动模式"开关
- **降级**：`supportsToolCalling=false` → 现有 `<tableEdit>` 文本协议 + 关键词匹配，体验不变

### 2) 所需调用的模型能力组合
- **工具调用（必须）**：主动检索 + 表格整理 + 记忆
- **文本生成（必须）**：角色入戏回复
- **视觉（可选）**：若用户发图（方向 1 多模态对话），AI 可结合图片调用工具
- 组合：`supportsToolCalling && supportsText`（+可选 `supportsVision`）

### 3) 预期提升的用户体验或业务指标
- **用户体验**：角色"有心智"——会主动查设定、会自己整理状态表、长会话不失忆；从"问答机器"升级为"有记忆的伙伴"
- **业务指标**：设定一致性违规率 -30%（AI 主动查证而非靠关键词）；长会话（>50 轮）留存率提升；单会话平均消息数 +20%；用户感知"角色智能度"显著提升

### 4) 技术挑战及解决方案
| 挑战 | 解决方案 |
|------|---------|
| 工具调用增加首 token 延迟 | 仅在 AI 判定需要时调用（非每轮必调）；UI loading 缓解感知 |
| AI 滥用 `updateStateTable` 误改状态 | 关键字段变更需用户确认（设置开关：自动/确认）；写操作默认走"草稿"区，用户审阅后应用 |
| 主动行动模式可能打断用户 | 默认关闭；开启后限制频率（每 N 轮最多 1 次主动）；可随时打断 |
| 长会话工具调用历史膨胀 | 工具调用结果不全部入历史，仅保留摘要；`role:'tool'` 消息可压缩 |
| 不同角色卡对工具需求不同 | 工具集可在角色卡配置中按需启用（如推理型角色启用更多检索工具） |

## 方向 B：写作模式 → 写作智能体

### 功能概述
将写作模式从"用户逐个点击生成/审核/修复"升级为"自驱写作智能体"：用户给出高层指令（如"按大纲写第 5-8 章并保证剧情一致"），AI 自主完成「读大纲→生成章节→自审剧情→自动修复→更新表格→进入下章」的闭环，过程中可调用 PlotCheckerService、OutlineGenerator、DescriptionPolisher、TableOrganizeService 等现有服务作为工具。用户可随时介入/中断/审阅。

### 1) 具体实现方案
- **工具集**（启用写作组）：
  - `readOutline()` / `updateOutline(chapterIndex, patch)` — 读改大纲
  - `writeChapter(index, content)` — 调用 AIAssistedChapterService 生成章节（支持分块/迭代）
  - `checkPlot(chapterIndex)` — 复用 PlotCheckerService 返回 5 维报告 + issues
  - `applyAutoFix(issueId)` — 应用 PlotChecker 的 autoFix diff
  - `polishText(text)` — 复用 DescriptionPolisher
  - `updateWritingTable(commands)` — 自主更新章节/角色/情节表
  - `searchWorldbook(query)` — 写作时查世界书设定
- **写作智能体编排**（新增 `WritingAgentService.ts`）：
  - 接收高层任务（如 `{type:'writeRange', fromChapter:5, toChapter:8, ensureConsistency:true}`）
  - 编排循环：`readOutline → writeChapter → checkPlot → 若有 issues 则 applyAutoFix → 再 checkPlot 确认 → updateWritingTable → 下一章`
  - 每步通过 IPC 事件推送进度（`writing:agentProgress`），前端实时显示"正在写第 5 章… 正在审核… 发现 2 处问题，修复中…"
- **前端**（TableOrganizeMainPanel / WritingMode 新增"智能体任务"面板）：
  - 任务输入框（高层指令）+ 任务列表（进行中/已完成）
  - 实时进度流 + 每步产物预览（章节草稿/审核报告/diff）
  - 用户可随时"暂停/介入编辑/继续"；每章完成后需用户确认或自动继续（可配置）
- **降级**：`supportsToolCalling=false` → 回退到现有"用户逐个点击"模式

### 2) 所需调用的模型能力组合
- **工具调用（必须）**：编排多步写作工作流
- **文本生成（必须）**：章节生成、审核报告、修复
- 组合：`supportsToolCalling && supportsText`

### 3) 预期提升的用户体验或业务指标
- **用户体验**：从"手动操作 5 个按钮写一章"到"一句话指令写多章并自审"；作者专注创意决策，机械工作交给智能体
- **业务指标**：单章产出耗时 -50%（预估）；剧情一致性违规率 -40%（每章自动审核+修复）；用户写作完成率 +30%；表格与章节同步率 100%（自动更新）

### 4) 技术挑战及解决方案
| 挑战 | 解决方案 |
|------|---------|
| 长任务中断/崩溃导致进度丢失 | 每步落盘 checkpoint；任务可断点续跑；章节草稿版本化（复用 ChatVersionService 模式） |
| AI 自主修复可能偏离作者意图 | autoFix 默认走"建议"而非"直接应用"；关键章节需用户确认；保留原版可一键回退 |
| 工具调用循环 token 消耗大 | 章节内容传引用而非全文（传 chapterIndex）；审核报告只传 issues 摘要 |
| 长篇多章状态膨胀 | `getCharacterState` 返回摘要；定期压缩历史章节为摘要 |
| PlotChecker 误报导致死循环修复 | 修复次数硬上限（每章 max 3 轮）；超限标记"需人工审核"并跳过 |
| 不同小说类型流程不同 | 任务模板化（web_novel / serious_fiction 不同流程）；可在 WritingConfigPanel 配置 |

## 方向 C：世界书 → AI 自驱编写

### 功能概述
将世界书从"用户手动创建+手动触发 AI 生成"升级为"AI 自驱维护"：AI 在对话/写作过程中自主发现新实体（地点/角色/物品/设定）并创建世界书条目；自主对现有条目做关键词补全、去重、合并、动态排序；世界书注入从被动关键词匹配升级为 AI 主动检索。现有 15+ AI 操作从"用户点击"变为"智能体按需调用"。

### 1) 具体实现方案
- **工具集**（启用世界书组）：
  - `searchEntries(query)` — 复用 ChatVectorizationService 语义检索
  - `createEntry(entry)` — 创建条目（标记 `autoGenerated:true`，可复用现有字段）
  - `updateEntry(uid, patch)` — 更新条目内容/关键词
  - `mergeEntries(uids)` / `deduplicateEntries()` — 去重合并
  - `generateKeywords(content)` — 复用现有 AI 关键词生成
  - `expandFromContext(contextText)` — 从对话/章节文本中提取新实体并生成条目
  - `sortEntries()` — 复用现有 handleAISortEntries 逻辑
- **三模式集成点**：
  - **对话中**：每 N 轮对话后，AI 自主调用 `expandFromContext(recentDialogue)` 发现新实体→`createEntry`；用户可审阅 autoGenerated 条目并确认/删除
  - **写作中**：每章生成后，写作智能体调用 `expandFromContext(chapterContent)` 自动扩展世界书
  - **独立世界书管理**：新增"AI 自主整理"按钮——AI 调用 `deduplicateEntries` + `generateKeywords` + `sortEntries` 一键维护
- **注入升级**：对话/写作时，AI 用 `searchEntries(query)` 主动检索替代被动关键词匹配（方向 0 检索工具的复用）
- **autoGenerated 条目审阅流**：前端新增"待审阅"区，列出 AI 自创建的条目，用户可批量确认/编辑/删除
- **降级**：`supportsToolCalling=false` → 现有手动触发 + 关键词匹配

### 2) 所需调用的模型能力组合
- **工具调用（必须）**：自主调用增删改查工具
- **文本生成（必须）**：条目内容生成、关键词提取
- 组合：`supportsToolCalling && supportsText`

### 3) 预期提升的用户体验或业务指标
- **用户体验**：世界书"自我生长"——用户不用手动建档，AI 边聊边写边积累；世界书始终保持最新/去重/有序
- **业务指标**：世界书条目覆盖度 +50%（AI 自主发现用户忽略的实体）；世界书注入命中率 +30%（主动检索 vs 被动关键词）；用户世界书维护耗时 -60%；长篇创作设定遗漏率显著下降

### 4) 技术挑战及解决方案
| 挑战 | 解决方案 |
|------|---------|
| AI 误创建低质量/重复条目 | 新建条目入"待审阅"区，默认不启用注入；用户确认后才 enabled |
| 自主创建条目泛滥 | 频率限制（每 N 轮/每章最多创建 K 条）；置信度阈值；用户可设上限 |
| 实体识别准确率 | `expandFromContext` 要求 AI 返回结构化 `{name, type, content, keywords, confidence}`；低置信度不入库 |
| 与用户手动条目冲突 | autoGenerated 条目带标记，不覆盖用户手动条目；合并需确认 |
| 向量索引与条目创建不同步 | createEntry 后同步调用 ChatVectorizationService 建索引 |
| 隐私/版权（写入真人信息） | 提示词约束"仅创建虚构设定"；不识别/记录真实人物信息 |

## 三维评估矩阵

| 方向 | 功能实用性 | 技术可行性 | 用户价值 | 综合优先级 |
|------|-----------|-----------|---------|-----------|

## 优先级建议与实施顺序

1. **第一波（P0，地基 + 核心诉求）**：
   - **方向 0（工具调用引擎）**：必须最先做，三模式共享底座。建议先支持 OpenAI 兼容协议 + 对话组/写作组/世界书组基础工具
   - **方向 B（写作智能体）**：用户核心诉求，且现有 PlotChecker/OutlineGenerator/AIAssistedChapterService 可直接工具化，收益最大
2. **第二波（P1，扩散到对话与世界书）**：
   - **方向 A（对话角色卡智能体）**：建立在方向 0 之上，对话组工具 + 状态确认机制
   - **方向 C（世界书自驱编写）**：现有 15+ AI 操作工具化 + autoGenerated 审阅流
3. **跨波协同**：方向 C 的 `expandFromContext` 可被方向 B 的写作智能体调用（每章生成后自动扩展世界书），建议方向 B 实现时预留对接点
