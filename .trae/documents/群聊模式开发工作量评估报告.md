#### 2.5.2 角色激活算法（独立实现）

参考 SillyTavern 设计理念，独立实现以下激活策略：

**NATURAL 模式（自然激活）**:
1. 检测用户输入中是否提及角色名称
2. 根据角色 `talkativeness` 属性进行概率激活
3. 保底机制：确保至少一个角色发言
4. 防止同一角色连续发言（`bannedUser` 机制）

**LIST 模式（列表顺序）**:
1. 按成员列表顺序依次激活
2. 去重处理

**POOLED 模式（池化随机）**:
1. 追踪上次用户发言后已发言的角色
2. 从未发言的角色池中随机选择
3. 如果全部发言过，排除最后发言者后随机选择

### 6.3 技术难点及解决方案

#### 难点 1: 多角色提示词构建的复杂度

**问题**: 在 APPEND 模式下，多个角色的 description、personality、scenario 需要合并为一个系统提示词，可能导致 AI 混淆不同角色的身份。

**解决方案** (参考 SillyTavern 设计理念):
1. 使用 `Join Prefix` 和 `Join Suffix` 模板清晰分隔各角色信息
2. 模板中注入角色名称标识，如 `=== [角色A] Description ===`
3. 支持用户自定义模板格式
4. 在 SWAP 模式下，每次只使用一个角色的完整上下文

#### 难点 2: 自然激活策略的命中率平衡

**问题**: NATURAL 模式下，可能所有角色都不被激活（提及检测 + 健谈度均未命中），导致无角色回复。

**解决方案** (参考 SillyTavern 设计理念):
1. 保底机制：如果无人激活，从健谈角色池中随机选择 1 个
2. 健谈度默认为 0.5（50% 概率发言），确保平均有角色回复
3. 防止同一角色连续发言（`bannedUser` 机制）

#### 难点 3: 消息完整性与数据一致性

**问题**: 群聊中可能涉及大量消息，并发写入或异常中断可能导致数据损坏。

**解决方案** (参考 SillyTavern 设计理念):
1. `chat_metadata.integrity` UUID 校验
2. `write-file-atomic` 原子写入
3. 自动备份到 `backups/` 目录
4. 保存失败时弹出确认对话框，避免静默覆盖

4. **优先核心**: Phase 2（激活算法 + 生成模式）是最大复杂度模块，建议优先投入精力
5. **并行开发**: Phase 3（UI）和 Phase 4（权限）可与 Phase 2 后期并行
6. **充分测试**: Phase 6 工作量占比 21%，建议不要压缩测试时间，**必须包含回归测试**
7. **参考 SillyTavern**: 已分析的技术文档可作为开发参考，但实现必须独立
