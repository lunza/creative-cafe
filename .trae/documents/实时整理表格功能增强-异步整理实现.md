# 实时整理表格功能增强计划 - 异步整理实现

## 一、 核心设计思路

本方案旨在将现有的"后台二次请求"同步整理模式，升级为"一次请求双输出"的异步整理模式。
- **同步整理**：保持现状，AI返回对话 → 后台再次请求AI整理表格。
- **异步整理**：AI返回对话 + 隐式标签包裹的整理命令 → 前端解析标签 → 调用后端直接执行命令 → 清洗标签后展示纯净对话。
- **架构原则**：提示词构建统一收敛至 `PromptBuilder.ts`；解析逻辑前置至消息接收端；执行逻辑复用现有表格服务。

## 二、 详细实施步骤

### 步骤 1：状态管理与 UI 交互实现
**目标**：实现互斥选项控制，默认同步，状态持久化。
1. **状态定义**：在 `CharacterDialogueChat.hooks.ts` 或对应 Store 中定义 `organizeMode: 'sync' | 'async' | 'off'`。
2. **UI 改造**：在 `CharacterDialogueChat.tsx` 的设置面板中，于"开启实时整理表格"开关下方渲染 `<Radio.Group>`。
   - 选项A：同步整理（默认）
   - 选项B：异步整理
   - 逻辑：开关关闭时禁用 Radio；开关打开时恢复上次选择或默认同步。
3. **配置同步**：确保该配置随角色对话配置保存至本地存储/数据库，跨会话保持。

### 步骤 2：提示词拼接逻辑改造 (`PromptBuilder.ts`)
**目标**：根据模式动态注入异步整理指令。
1. **接口扩展**：修改 `buildFinalSystemPrompt` 签名，新增参数：
   ```typescript
   buildFinalSystemPrompt(
     systemPrompt: string,
     vectorContextItems: ContextVectorItem[],
     memoryTableData?: string,
     organizeMode?: 'sync' | 'async' | 'off'
   )
   ```
2. **条件拼接**：当 `organizeMode === 'async'` 且 `memoryTableData` 存在时，在提示词末尾追加指令块：
   ```text
   --- 记忆表格异步整理指令 ---
   【任务】分析当前对话，生成表格整理命令。
   【输出格式】
   1. 优先输出完整的角色对话内容。
   2. 对话结束后，换行，严格使用以下隐式标签包裹命令：
   <!--  <tableEdit>
   insertRow(...)
   updateRow(...)
   </tableEdit> -->
   【约束】
   - 标签必须完整，不可截断或嵌套。
   - 若无新信息，仅输出对话，不输出标签。
   - 严格遵循增量更新：查唯一ID索引，已存在则 updateRow，新实体则 insertRow。
   - 命令需符合 tableEdit 解析器语法。
   【当前表格状态】
   {memoryTableData}
   ```
3. **规范约束**：确保所有拼接逻辑严格限定在 `PromptBuilder.ts` 内，不污染其他组件。

### 步骤 3：AI 回复解析与内容清洗
**目标**：精准提取命令，净化展示文本。
1. **拦截点**：在 `CharacterDialogueChat.hooks.ts` 的 `onComplete` 或消息落盘前拦截最终文本。
2. **正则提取**：使用严格正则匹配标签：
   ```typescript
   const ASYNC_TABLE_REGEX = /<!--\s*<tableEdit>([\s\S]*?)<\/tableEdit>\s*-->/gi;
   const match = aiResponse.match(ASYNC_TABLE_REGEX);
   ```
3. **分支处理**：
   - **命中标签**：
     1. 提取 `match[1]` 作为原始命令字符串。
     2. 使用 `aiResponse.replace(ASYNC_TABLE_REGEX, '').trim()` 获取纯净对话文本。
     3. 将纯净文本更新为最终展示内容。
     4. 触发异步执行流程（步骤4）。
   - **未命中**：直接展示原文本，视为AI未生成整理指令或对话无需整理。
4. **容错机制**：若解析失败或命令格式错误，仅记录警告日志，绝不阻断或修改用户可见的对话内容。

### 步骤 4：后端命令执行通道 (IPC)
**目标**：绕过耗时的逐条消息重处理，直接执行解析出的命令。
1. **服务暴露**：将 `chatLogService.ts` 中的 `executeTableEditCommands` 方法设为 `public`（若当前为 private）。
2. **IPC Handler**：在 `memoryHandlers.ts` 新增端点：
   ```typescript
   ipcMain.handle('memory:executeTableEditCommands', async (_, chatId, commands) => {
     return chatLogService.executeTableEditCommands(chatId, commands);
   });
   ```
3. **Preload 暴露**：在 `preload.ts` 的 `memory` 对象中挂载 `executeTableEditCommands` 方法。
4. **前端调用**：解析成功后，前端调用 `window.electronAPI.memory.executeTableEditCommands(chatId, parsedCommands)`。
5. **去重保护**：复用现有 `executeTableEditCommands` 中的去重逻辑（唯一ID校验+名称相似度校验），确保异步插入不会破坏数据一致性。

### 步骤 5：流程串联与边界处理
1. **流式输出兼容**：若 AI 支持流式输出，需确保标签完整输出后再触发解析（通常在 `onComplete` 阶段处理全量文本）。
2. **标签泄露防御**：在消息渲染组件（如 `ChatMessageBubble`）中增加二次过滤，作为最后一道防线，确保即使解析逻辑遗漏，UI 也不渲染原始标签。
3. **模式切换热更新**：用户切换同步/异步模式时，无需刷新页面，即时生效于下一次对话请求。

## 三、 关键技术细节

| 模块 | 关键技术点 | 说明 |
|:---|:---|:---|
| **正则解析** | `/<!--\s*<tableEdit>([\s\S]*?)<\/tableEdit>\s*-->/gi` | 支持跨行匹配，忽略首尾空白字符，全局搜索防遗漏 |
| **提示词注入** | 条件拼接 + 强约束示例 | 仅在异步模式注入，提供正反示例降低AI幻觉 |
| **执行通道** | 直接命令执行 vs 全量重算 | 异步模式跳过 `processChatProgressive` 的消息读取阶段，直接落盘，性能提升显著 |
| **数据一致性** | 后端去重锁 + 唯一ID索引 | 依赖已实现的 `canStartOrganize` 和 `executeTableEditCommands` 去重逻辑 |

## 四、 验证与测试方案

1. **同步模式回归测试**：开启同步整理，确认原有逻辑不受任何影响，表格正常更新。
2. **异步模式功能测试**：
   - 发送含新实体的消息，验证 AI 是否输出标签。
   - 验证 UI 是否仅展示纯净对话（无标签残留）。
   - 验证表格是否准确追加/更新数据。
3. **边界与异常测试**：
   - AI 未输出标签：系统正常显示对话，不报错。
   - 标签格式微偏差（如多余空格）：正则能否兼容。
   - 命令语法错误：后端捕获错误，前端提示日志，对话内容不受损。
4. **性能对比**：记录同步与异步模式下的端到端耗时，验证异步模式的延迟优势。
