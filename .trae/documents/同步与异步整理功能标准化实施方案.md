# 同步整理与异步整理标准化实施方案

## 一、现状对比分析

### 1.1 核心功能差异（需保留）

| 维度 | 同步整理 (processChatProgressive) | 异步整理 (processChatFull) |
|------|------|------|
| **触发时机** | AI回复完成自动触发（sync模式） | 用户手动触发（完全整理按钮） |
| **处理策略** | 增量处理，仅处理新增消息 | 完全重置，清空表格后处理全部消息 |
| **断点续传** | 支持，基于 processedCount 续传 | 不支持，每次从零开始 |
| **防抖间隔** | 默认 3000ms | 0ms（不允许并发即可） |
| **返回结果** | 多 `resumed` 字段 | 无 `resumed` 字段 |

### 1.2 不一致问题清单（需统一）

#### 问题 1：AbortController 缺失
- **同步整理**：有 AbortController，支持取消，`callAIAPIWithRetry` 传递 `signal`
- **异步整理**：无 AbortController，无取消机制，AI 调用不传 `signal`

#### 问题 2：日志前缀不一致
- **同步整理**：使用 `[Auto Organize]`
- **异步整理**：使用 `[Full Reorganize]`

#### 问题 3：safeChatId 计算代码重复
- 两个方法各自实现了一套完全相同的 safeChatId 计算逻辑（13行 replace 链），不符合 DRY 原则

#### 问题 4：表格快照/版本管理均未集成
- 两个方法在整理完成后都没有调用 `versionLinkerService` 或 `tableSnapshotService`
- 缺少统一的版本创建步骤

#### 问题 5：AI 参数默认值硬编码
- 同步整理和异步整理的 `aiConfig` 默认值完全相同但分别定义
- 默认 API URL、模型名称散布在两个方法中

#### 问题 6：消息处理核心循环代码重复率 >90%
- 两个方法的 `for` 循环内部（构建上下文、构建提示词、调用 AI、解析命令、执行命令、保存进度）几乎完全一致
- 唯一的区别是：同步整理从 `startIndex` 开始，异步整理从 `0` 开始

#### 问题 7：错误处理返回值不一致
- 同步整理：catch 中 `throw error`
- 异步整理：catch 中同样 `throw error`，但 finally 释放锁

## 二、标准化实施方案

### 原则：核心逻辑提取 + 差异化配置

将同步和异步整理的共同逻辑提取为私有方法 `processMessagesCore()`，通过配置对象控制差异化行为。

### 2.1 提取 safeChatId 计算为私有方法

```typescript
private getSafeChatId(chatId: string): string {
  return chatId
    .replace(/\//g, '_')
    .replace(/\\/g, '_')
    .replace(/\s+/g, '_')
    .replace(/@/g, '_')
    .replace(/-/g, '_')
    .replace(/:/g, '_')
    .replace(/\*/g, '_')
    .replace(/\?/g, '_')
    .replace(/"/g, '_')
    .replace(/</g, '_')
    .replace(/>/g, '_')
    .replace(/\|/g, '_');
}
```

### 2.2 统一日志前缀为 [TableOrganize]

所有整理相关日志统一使用 `[TableOrganize]` 前缀，通过子标识区分类型：
- 同步整理：`[TableOrganize][Sync]`
- 异步整理：`[TableOrganize][Full]`

### 2.3 提取核心消息处理逻辑为私有方法

```typescript
private async processMessagesCore(
  chatId: string,
  effectiveTemplateId: string,
  targetMessages: ChatMessage[],
  aiConfig: { apiKey: string; apiUrl: string; modelName: string; apiMode: string },
  apiEndpoint: string,
  template: any,
  startIndex: number,
  totalMessages: number,
  controller: AbortController,
  onProgress?: (current: number, total: number, message: string, percent?: number) => void,
  logPrefix?: string
): Promise<{ processedCount: number; errorCount: number; errors: string[] }>;
```

该方法包含：
- for 循环遍历消息
- 取消检查（checkAborted）
- 进度回调
- 构建表格上下文
- 构建 AI 提示词
- 调用 AI API（带 signal）
- 解析 tableEdit 命令
- 执行命令
- 保存进度
- 错误捕获和记录

### 2.4 为异步整理添加 AbortController

```typescript
// processChatFull 方法中
const controller = new AbortController();
this.organizeAbortControllers.set(chatId, controller);
// finally 中
this.organizeAbortControllers.delete(chatId);
```

### 2.5 统一表格快照创建

整理完成后（成功时），统一调用 `tableSnapshotService.createSnapshot` 创建表格快照版本：

```typescript
private async createTableSnapshotAfterOrganize(
  chatId: string,
  characterCardName: string,
  versionLinkId: string
): Promise<string | null>;
```

### 2.6 重构后的方法结构

```typescript
// processChatProgressive - 同步整理（增量）
public async processChatProgressive(...) {
  // 1. 参数校验、防抖、加锁
  // 2. 创建 AbortController
  // 3. 读取消息、过滤、排序
  // 4. 计算 startIndex（增量逻辑）
  // 5. 获取模板、配置 AI
  // 6. 调用 processMessagesCore(targetMessages, startIndex, ...)
  // 7. 整理完成后创建表格快照
  // 8. 标记会话状态、返回结果
}

// processChatFull - 异步整理（完全）
public async processChatFull(...) {
  // 1. 参数校验、加锁
  // 2. 创建 AbortController
  // 3. 读取消息、过滤、排序
  // 4. startIndex = 0（完全重置）
  // 5. 获取模板、配置 AI
  // 6. 调用 processMessagesCore(targetMessages, 0, ...)
  // 7. 整理完成后创建表格快照
  // 8. 标记会话状态、返回结果
}
```

### 2.7 统一存储路径和版本管理

整理完成后的统一后处理流程：

```typescript
private async postOrganizeCleanup(
  chatId: string,
  characterCardName: string,
  organizeType: 'sync' | 'full'
): Promise<void>;
```

包含：
1. 调用 `tableSnapshotService.createSnapshot` 创建表格快照
2. 调用 `versionLinkerService.getVersionIndex` 获取版本索引
3. 在版本索引中添加当前整理的记录
4. 记录变更日志

### 2.8 统一错误处理

所有整理方法统一使用以下错误处理模板：

```typescript
try {
  // 核心逻辑
} catch (error) {
  addLog(`[${logPrefix}] 整理失败: ${error}`, 'error');
  // 回滚表格数据
  this.rollbackTableData(tableDataBackup, tableFilePath);
  // 发送失败通知
  this.sendOrganizeNotification(chatId, `整理失败: ${error}`, 'error');
  result.success = false;
  result.errors.push(error instanceof Error ? error.message : String(error));
  throw error;
} finally {
  this.organizeAbortControllers.delete(chatId);
  this.releaseOrganizingLock(chatId);
}
```

## 三、实施步骤

### 步骤 1：提取公共工具方法
- 提取 `getSafeChatId` 方法
- 提取 `sendOrganizeNotification` 方法
- 提取 `rollbackTableData` 方法
- 提取 `buildOrganizeConfig` 方法（统一 AI 配置默认值）

### 步骤 2：统一日志前缀
- 将 `[Auto Organize]` 和 `[Full Reorganize]` 替换为 `[TableOrganize][Sync]` 和 `[TableOrganize][Full]`

### 步骤 3：提取核心处理逻辑
- 创建 `processMessagesCore` 私有方法
- 将两个方法中的 for 循环逻辑迁移到此方法
- 为异步整理的 AI 调用添加 `controller.signal`

### 步骤 4：为异步整理添加 AbortController
- 在 `processChatFull` 中创建 AbortController
- 传递给 `processMessagesCore`
- finally 中清理

### 步骤 5：添加统一的后处理流程
- 在两个方法的整理成功后调用 `postOrganizeCleanup`
- 创建表格快照
- 更新版本索引

### 步骤 6：简化 processChatProgressive 和 processChatFull
- 删除重复代码
- 仅保留差异化逻辑（防抖、startIndex 计算、完全重置等）
- 调用公共方法完成核心处理

### 步骤 7：构建验证
- 编译通过
- 同步整理功能正常
- 异步整理功能正常
- 停止整理功能正常

## 四、风险评估

1. **低风险**：提取公共方法、统一日志前缀、添加 AbortController
2. **中风险**：重构核心处理循环，需确保行为一致
3. **缓解措施**：重构前后分别进行功能测试，确保行为不变
