# Creative Cafe 技术文档

## 开发规范

### 【优先级最高】禁止设置 AI 参数默认值

**规则**：在调用 AI 引擎时，所有参数（包括但不限于 Temperature、MaxTokens、Model 等）必须从系统设置中动态获取，**绝对禁止**设置任何默认值。

**原因**：
1. 默认值会掩盖参数缺失的问题，导致错误难以定位
2. 当参数配置错误时，系统应直接抛出明确异常，提示用户修正，而非静默使用默认值继续执行
3. 使用默认值可能导致用户以为功能正常，但实际行为与预期不符

**正确做法**：
```typescript
// ✅ 正确：参数缺失时抛出明确错误
const temperature = Number(activeEngine.temperature);
if (!temperature && temperature !== 0) {
  throw new Error('AI 引擎未配置 temperature 参数，请在设置中配置');
}

const maxTokens = Number(activeEngine.max_tokens);
if (!maxTokens) {
  throw new Error('AI 引擎未配置 max_tokens 参数，请在设置中配置');
}
```

**错误做法**：
```typescript
// ❌ 错误：使用默认值掩盖问题
const temperature = activeEngine.temperature || 0.7;  // 禁止！
const maxTokens = activeEngine.max_tokens ?? 4000;    // 禁止！
const model = activeEngine.model || 'gpt-4o';         // 禁止！
```

**适用范围**：
- 所有 AI 请求相关代码（写作模式、聊天模式、世界书生成、角色卡生成等）
- 前端组件和后端服务
- IPC 处理器和工具函数

**实施日期**：2026-05-24
**相关修复**：fix-table-organize-ai-parameters

### 【优先级最高】前端获取系统设置的 IPC API 路径规范

**规则**：在渲染进程中获取系统设置时，必须使用 `window.electronAPI.setting.load()`，**绝对禁止**使用不存在的 API（如 `window.electronAPI.settings.getSettings()`）。

**原因**：
1. 错误的 IPC API 路径会导致 `Cannot read properties of undefined (reading 'getSettings')` 运行时错误
2. 前端 IPC API 定义位于 `electron.d.ts`，新增 API 前必须先在类型定义中声明

**正确做法**：
```typescript
// ✅ 正确：使用 electron.d.ts 中定义的 API
const settingResponse = await window.electronAPI.setting.load();
if (!settingResponse.success) {
  throw new Error('无法获取系统设置');
}

const setting = settingResponse.setting;
const activeEngineId = setting?.activeEngineId;
const engines = setting?.aiEngines || [];
const activeEngine = engines.find((e: any) => e.id === activeEngineId) || engines[0];
```

**错误做法**：
```typescript
// ❌ 错误：使用不存在的 API 路径
const settingsResponse = await window.electronAPI.settings.getSettings();  // 禁止！此 API 不存在
```

**API 定义对照表**：
| 功能 | 正确 API | 返回值类型 |
|------|---------|-----------|
| 获取系统设置 | `window.electronAPI.setting.load()` | `{ success: boolean; setting?: any; error?: string }` |
| 保存系统设置 | `window.electronAPI.setting.save(setting: any)` | `{ success: boolean; error?: string }` |
| 获取配置路径 | `window.electronAPI.setting.getPath()` | `{ success: boolean; path?: string; error?: string }` |

**注意事项**：
- 注意 `setting`（单数）和 `settings`（复数）的拼写差异，实际 API 使用单数 `setting`
- 返回值结构是 `{ setting: any }` 而非 `{ settings: any }`
- 新增任何 IPC API 前，必须先更新 `src/renderer/types/electron.d.ts` 中的类型定义

**适用范围**：
- 所有需要读取系统配置的前端组件
- 所有涉及 AI 引擎配置的功能模块

**实施日期**：2026-05-24
**相关修复**：fix-table-organize-ai-parameters

## 架构概览

Creative Cafe 是一个基于 Electron + React + TypeScript 的跨平台桌面 AI 创意助手应用。项目包含以下主要技术栈：

- **主进程**: Electron (Node.js)
- **渲染进程**: React 17 + TypeScript + Ant Design 4.x + Monaco Editor
- **状态管理**: React Hooks (useState, useRef, useEffect, useReducer)
- **AI 服务**: 支持多种 OpenAI 兼容 API 的 AI 引擎
- **数据库**: SQLite（通过 better-sqlite3-multiple-ciphers）
- **打包工具**: Electron Builder

## System Prompt 拼接架构

### 问题描述

在 v1.0.0 及之前版本中，以下功能模块未正确拼接设置中的全局 `system_prompt`：
- 世界书 AI 生成（WorldBookEditor.tsx）
- 角色对话（CharacterDialogueChat.hooks.ts）

### 修复方案

采用**方案一：在各功能模块中分别进行 system_prompt 拼接**。

选择理由：
1. `aiHandlers.ts` 是底层 IPC 转发层，只接收 HTTP 请求配置（URL/headers/body），不持有 `AIEngine` 对象
2. 要实现统一集中拼接需要重构整个 AI 请求传递链路，改动巨大
3. 系统已有 4 个模块正确实现了拼接逻辑，说明此模式稳定可靠

### 拼接模式

所有涉及 AI 请求的模块遵循统一的拼接模式：

```typescript
// 拼接全局 system_prompt
let finalSystemPrompt = taskSpecificPrompt;
if (activeEngine.system_prompt && activeEngine.system_prompt.trim()) {
  finalSystemPrompt = activeEngine.system_prompt.trim() + '\n\n' + taskSpecificPrompt;
}
```

### 模块清单

| 模块 | 文件位置 | 拼接状态 | 说明 |
|------|---------|---------|------|
| 角色卡管理-翻译 | `CharacterManager.tsx` L630-633 | ✅ 已拼接 | 翻译功能 |
| 角色卡管理-生成 | `CharacterManager.tsx` L808-811 | ✅ 已拼接 | 角色生成 |
| 角色卡管理-润色 | `CharacterManager.tsx` L953-956 | ✅ 已拼接 | 润色优化 |
| Markdown编辑器AI工具 | `MarkdownAITools.tsx` L404-410 | ✅ 已拼接 | AI辅助编辑 |
| **世界书AI生成** | `WorldBookEditor.tsx` L222-226 | ✅ **已修复** | 2026-05-12 修复 |
| **角色对话** | `CharacterDialogueChat.hooks.ts` L652-656 | ✅ **已修复** | 2026-05-12 修复 |

### 修复详情

#### 1. WorldBookEditor.tsx

**修复前**：直接使用模板的 `systemPrompt`，未拼接全局 `system_prompt`

**修复后**（L222-226）：
```typescript
if (apiMode === 'chat_completion') {
  let finalSystemPrompt = template.systemPrompt;
  if (activeEngine.system_prompt && activeEngine.system_prompt.trim()) {
    finalSystemPrompt = activeEngine.system_prompt.trim() + '\n\n' + template.systemPrompt;
  }
```

#### 2. CharacterDialogueChat.hooks.ts

**修复前**：`buildCompleteSystemPrompt` 只构建角色相关提示词，未包含全局 `system_prompt`

**修复后**（L652-656）：
```typescript
// 拼接全局system_prompt到角色提示词
const globalSystemPrompt = activeEngine.system_prompt?.trim();
const effectiveSystemPrompt = globalSystemPrompt 
  ? globalSystemPrompt + '\n\n' + finalSystemPrompt
  : finalSystemPrompt;
```

同时在 token 计数（L679）和消息发送（L1017）处统一使用 `effectiveSystemPrompt`。


### 2026-05-17: 角色卡对话异步整理模式表格自动创建功能失效修复 ⭐

- **问题**: 角色卡对话启用异步整理模式（async）时，AI 生成的 tableEdit 命令执行失败，TableTemplateService 多次报告"表格文件不存在"
- **影响**: 异步整理模式下所有表格编辑命令（insertRow/updateRow/deleteRow）均无法执行
- **根因（第一轮发现）**: 
  - 同步整理模式（`processChatProgressive`）在执行命令前会显式检查并创建表格文件（L2535-2560）
  - 异步整理模式直接调用 `executeTableEditCommands`（L1166），该方法内部缺少表格文件存在性检查逻辑
  - `autoInitializeChatSession` 仅在 `getTableData` 的 fallback 路径中触发，异步整理模式不会调用此路径
- **第一轮修复**: 在 `chatLogService.executeTableEditCommands` 方法开头添加表格文件存在性检查，若不存在则自动创建
  - 优先使用已关联的模板（通过 `getAssociatedTemplate` 查询）
  - 若无关联模板则使用默认模板（`getAllTemplates` 取第一个）
  - 使用与 `processChatProgressive` 一致的 `safeChatId` 计算逻辑（12种特殊字符替换）
  - 修改文件: `src/main/services/memory/chatLogService.ts`（executeTableEditCommands 方法 L1174-L1211）
- **根因（第二轮发现 - 用户反馈后）**: 
  - 即使第一轮修复后，`getTableData` fallback 路径中的 `autoInitializeChatSession` 仍然失败
  - 场景：关联记录存在（`associations.json` 中有记录）但表格文件已被删除/清理
  - `autoInitializeChatSession` 仅检查关联记录是否存在，不验证实际表格文件，导致有记录但文件缺失时跳过初始化
- **第二轮修复**: 在 `autoInitializeChatSession` 方法中添加表格文件存在性验证
  - 若关联存在且文件存在 → 跳过（正常情况）
  - 若关联存在但文件缺失 → 使用关联模板的 `templateId` 调用 `createTableFile` 重建表格文件
  - 若无关联 → 使用默认模板调用 `associateTemplate` 完成完整初始化
  - 修改文件: `src/main/services/memory/chatLogService.ts`（autoInitializeChatSession 方法 L3169-L3235）
- **根因（第三轮发现 - 用户再次反馈）**: 
  - `associateTemplate` 创建的副本模板（如 `st-memory-enhancement-default_狼人杀助手2.0_1778522830757`）可能在清理数据时被删除，但 `associations.json` 中的关联记录仍然存在
  - 当 `executeTableEditCommands` 或 `autoInitializeChatSession` 使用该副本模板ID调用 `createTableFile` 时，`getTemplate` 返回 `null`，导致"模板不存在"异常
  - 第一轮和第二轮修复都没有处理"关联的副本模板不存在"的边界情况
- **第三轮修复（系统性综合修复）**:
  - 新增 `resolveAvailableTemplate` 私有方法（L2146）：统一处理模板回退逻辑
    - 优先使用关联的副本模板（若存在）
    - 副本模板不存在时，回退到第一个非副本原始模板
    - 无原始模板时，使用第一个可用模板
    - 所有路径均返回 null 时表示无任何可用模板
  - 修改 `executeTableEditCommands`：使用 `resolveAvailableTemplate` 替代原有的 `getAssociatedTemplate` + 手动回退逻辑
    - 增加文件创建后的二次验证（`fs.existsSync`），确保文件确实写入成功
    - 增加 `表格文件已存在` 的 debug 日志，便于排查路径一致性问题
  - 修改 `autoInitializeChatSession`：重建逻辑也使用 `resolveAvailableTemplate`，避免副本模板缺失导致的静默失败
  - 修改文件: `src/main/services/memory/chatLogService.ts`
- **标记**: ⭐ 重点标记 - 核心功能 Bug 修复，经过三轮迭代修复完成

### 2026-05-17: AI 响应中 HTML 注释封装对象解析兼容性修复 ⭐

- **问题**: AI 在 tableEdit 命令的 JSON 数据值中嵌入 HTML 注释（如 `"3":"露娜<!-- 兽 -->"`）时，解析器完全失效，所有命令无法执行
- **影响**: 所有包含嵌套 HTML 注释的 tableEdit 命令全部解析失败
- **根因**: 
  - `tableEditParser.extractCommentText` 使用非贪婪正则 `<!--([\s\S]*?)-->` 匹配所有 HTML 注释
  - 当 AI 在数据值中嵌入嵌套注释（如 `"朱迪<!-- 药 -->"`）时，非贪婪正则会匹配到最近的 `-->`，导致外层注释被截断
  - 例如：`<!-- \ninsertRow(2, {"3":"朱迪<!-- 药 -->"}) \n-->` 被截断为 `\ninsertRow(2, {"3":"朱迪` + ` 药 ` + 剩余内容
  - `JSON.parse` 对截断的数据失败 → 所有命令解析失败
- **修复**: 
  - 重写 `parseCommands` 方法：不再依赖 `extractCommentText` 提取 HTML 注释，改为直接按行匹配 `insertRow(...)`/`updateRow(...)`/`deleteRow(...)` 命令
  - 增强 `parseDataObject` 方法：在解析 JSON 前，使用 `dataStr.replace(/<!--[\s\S]*?-->/g, '')` 清理嵌套 HTML 注释
  - 修改文件: `src/main/services/memory/tableEditParser.ts`（parseCommands L105-L133, parseDataObject L268-L306）
- **标记**: ⭐ 重点标记 - 核心功能 Bug 修复
