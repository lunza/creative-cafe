# 表格快照与聊天记录版本统一整合实施方案

## 一、现状分析

### 1.1 当前存储结构

```
data/memories/
├── chats/                          # 聊天记录存储（新架构）
│   └── {角色卡名称}/
│       ├── {chatId}.json           # 主聊天记录文件
│       └── versions/               # 聊天记录版本目录
│           ├── 1_{角色卡名称}_{timestamp}.json
│           ├── 2_{角色卡名称}_{timestamp}.json
│           └── ...
├── chatlog/                        # 表格文件存储（旧架构）
│   ├── {safeChatId}.json           # 当前表格数据
│   └── snapshots/                  # 表格快照目录
│       ├── {角色卡名称}_{timestamp}{随机串}.json
│       └── ...
└── templates/                      # 表格模板
    └── {templateId}.json
```

### 1.2 现存问题

- **存储路径分散**：聊天记录版本在 `chats/` 下，表格快照在 `chatlog/snapshots/` 下
- **命名规则不统一**：两者使用完全不同的命名格式
- **无关联标识**：无法通过某个版本快速定位对应的表格快照
- **版本创建时机不一致**：聊天记录版本在 saveTestChat 时创建，表格快照创建时机不明确
- **无一致性校验**：无法验证某个聊天版本与表格快照是否属于同一时间点
- **缺乏变更追踪**：无法追溯表格与聊天记录的关联修改历史

## 二、设计目标

建立统一的 `VersionLinker`（版本关联器）机制，实现：

1. **统一版本标识**：每次创建版本时生成唯一 `versionLinkId`
2. **双向关联查询**：通过 versionLinkId 可以同时找到聊天版本和表格快照
3. **统一存储结构**：将快照迁移至统一的 versions 目录
4. **变更追踪日志**：记录每次版本创建的时间、类型、触发原因
5. **一致性校验**：定期验证聊天版本与表格快照的版本匹配情况

## 四、核心服务设计

### 4.1 VersionLinkerService（版本关联服务）

```typescript
class VersionLinkerService {
  // 生成统一版本关联ID
  generateVersionLinkId(): string;

  // 创建关联版本（同时创建聊天版本+表格快照）
  async createLinkedVersion(characterCardName: string, options: {
    messages?: any[];
    tableData?: any;
    metadata?: any;
    triggerType?: 'auto' | 'manual' | 'aiOrganize';
  }): Promise<VersionLinkRecord>;

  // 获取版本索引
  async getVersionIndex(characterCardName: string): Promise<VersionIndex>;

  // 根据 versionLinkId 获取关联的聊天版本和表格快照
  async getLinkedVersion(characterCardName: string, versionLinkId: string): Promise<{
    chatVersion: any | null;
    tableSnapshot: any | null;
    linkRecord: VersionLinkRecord;
  }>;

  // 一致性校验
  async verifyConsistency(characterCardName: string): Promise<ConsistencyReport>;

  // 获取变更日志
  async getChangeLog(characterCardName: string, options?: { limit?: number }): Promise<ChangeLogEntry[]>;

  // 迁移旧快照到新结构
  async migrateOldSnapshots(characterCardName: string): Promise<MigrationResult>;
}
```

### 4.2 TableSnapshotService（表格快照服务）

从 `tableTemplateService` 中拆分出独立的快照管理逻辑：

```typescript
class TableSnapshotService {
  // 创建表格快照
  async createSnapshot(characterCardName: string, tableData: any, versionLinkId: string): Promise<string>;

  // 获取快照列表
  async getSnapshots(characterCardName: string): Promise<TableSnapshot[]>;

  // 获取快照内容
  async getSnapshotContent(filePath: string): Promise<any>;

  // 删除快照
  async deleteSnapshot(filePath: string): Promise<boolean>;
```

## 六、数据迁移方案

### 6.1 迁移流程

1. 应用启动时检测是否存在 `chatlog/snapshots/` 目录
2. 如果存在，执行迁移：
   - 读取旧快照文件列表，按时间戳排序
   - 为每个旧快照分配 sequenceNumber
   - 复制到 `versions/table/` 目录，使用新命名格式
   - 在 version-index.json 中创建对应条目（chatVersion.exists=false）
   - 写入 change-log 记录迁移操作
3. 迁移完成后，重命名旧目录为 `chatlog/snapshots.migrated/`（保留备份）
4. 下次启动时不再执行迁移

### 6.2 迁移安全保障

- 迁移过程中不删除原始文件
- 迁移失败时回滚已复制的文件
- 记录迁移日志到 `logs/migration.log`
- 提供手动触发迁移的 IPC 接口

## 七、风险与回退方案

### 7.1 风险点

1. **数据迁移失败**：旧快照文件格式不兼容
2. **性能影响**：版本索引文件过大影响加载
3. **版本冲突**：并发创建版本导致序号冲突

### 7.2 回退方案

1. 迁移前备份所有旧快照文件
2. 版本索引文件超过 1000 条时自动归档历史记录
3. 使用文件锁或时间戳保证版本序号唯一性
4. 保留旧存储路径的兼容性，新功能不使用时不影响现有逻辑
