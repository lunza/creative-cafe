## 第二部分：编码规范 / 检查清单（预防类似问题）

以下规范基于历史 bug 修复经验总结，用于预防同类问题再次发生。每次提交代码审查时，请对照相关章节的检查清单逐项确认。

### 2.1 Prompt 工程编码规范

**适用场景**: 任何构建系统提示（system prompt）发送给 LLM 的代码，包括 `buildPolishInputSystemPrompt`、`buildUserReplySystemPrompt`、`buildDialoguePrompt`、`buildContinuationPrompt` 等。

#### 规范 1：任务框架（Task Framing）一致性

系统提示的**任务定义层**（开头第一句话）必须明确、唯一地声明任务类型。任务类型一旦确定，**整个系统提示中不得残留其他任务类型的语义触发词**。

**常见任务类型与对应触发词**:

| 任务类型 | 合理的措辞 | 错误的措辞（会触发任务混淆） |
|---|---|---|
| 文本润色 / 扩写 | "润色"、"扩展"、"优化"、"输出润色后的文本" | "生成回复"、"续写"、"回答"、"确保上下文连贯" |
| 对话回复生成 | "生成回复"、"自然衔接"、"推进对话" | "润色"、"扩写"（除非明确要求扩展回复长度） |
| 文本续写 | "续写"、"继续上一条消息" | "润色"、"生成新回复" |
| 问答 / 信息抽取 | "回答"、"提取"、"总结" | "生成对话"、"扮演角色" |

**检查清单**:
- [ ] 开头任务定义是否包含明确的任务类型声明？
- [ ] 开头任务定义是否包含"禁止做什么"的负面约束（防止 LLM 走默认路径）？
- [ ] 任务要求每一条是否与开头任务定义一致？没有混入其他任务类型的措辞？
- [ ] personConstraint（人称视角约束）是否使用了与任务类型匹配的动词（润色任务用"输出"，对话任务用"生成回复"）？

#### 规范 2：孪生函数差异化

当一个功能存在两个相似的"孪生函数"（如 `buildPolishInputSystemPrompt` 与 `buildUserReplySystemPrompt`），**两个函数的系统提示必须有显著差异**，不能复用相同的措辞模板仅替换关键词。

**反模式**:
```typescript
// 反模式：两个函数的 personConstraint 完全相同
function buildPolishInputSystemPrompt(...) {
  personConstraint = `以第一人称（"我"）视角生成回复，使用"我"作为自称`;  // 错误
}
function buildUserReplySystemPrompt(...) {
  personConstraint = `以第一人称（"我"）视角生成回复，使用"我"作为自称`;  // 合理
}
```

**正模式**:
```typescript
// 正模式：润色函数使用"输出"，回复函数使用"生成回复"
function buildPolishInputSystemPrompt(...) {
  personConstraint = `润色后的文本以第一人称（"我"）视角输出，使用"我"作为自称`;  // 润色任务用"输出"
}
function buildUserReplySystemPrompt(...) {
  personConstraint = `以第一人称（"我"）视角生成回复，使用"我"作为自称`;  // 对话任务用"生成回复"
}
```

**检查清单**:
- [ ] 是否对比了孪生函数的措辞差异？
- [ ] 孪生函数共用的措辞（如 personConstraint）是否在两个上下文中都合理？
- [ ] 任务要求段落是否针对各自任务类型定制，而非简单替换关键词？

#### 规范 3：关键约束的位置与强度

LLM 对系统提示的 attention 路径**前重后轻**——出现在前面的内容约束力更强，出现在后面的内容容易被稀释。关键约束（"不要做什么"）应**前置**到待处理对象之前，让 LLM 在看到待处理对象时已经明确约束。

**反模式**:
```markdown
## 待润色文本
<polish_target>
你吃饭了吗
</polish_target>

## 关键约束
- 不要回答上述问题
```
（LLM 先看到 `<polish_target>` 内的问句，已构建"需要回答"的认知，后置约束被稀释）

**正模式**:
```markdown
## 关键约束
- **绝对禁止**回答 <polish_target> 内的任何问题
- **绝对禁止**生成对话回复

## 待润色文本
<polish_target>
你吃饭了吗
</polish_target>
```
（LLM 先看到约束，再看到待润色对象，约束力最大化）

**强度措辞**：使用"**绝对禁止**"（粗体 + 强否定）比"不要"（弱否定）更有效。明确列出禁止的行为类型（"包括 AI 角色回复、用户回复、续写对话"）比泛泛的"不要回答"更具体。

**检查清单**:
- [ ] 关键约束是否位于待处理对象（`<polish_target>` 等）之前？
- [ ] 关键约束是否使用强禁止措辞（"绝对禁止"）而非弱否定（"不要"）？
- [ ] 关键约束是否明确列出禁止的行为类型，便于 LLM 识别？

#### 规范 4：上下文注入的最小化原则

系统提示中注入的上下文（角色信息、对话历史、人设等）应**最小化**，仅保留与任务直接相关的字段。多余的上下文（如角色个性、角色描述）可能触发 LLM 进入"角色扮演"模式，与任务定义冲突。

**反模式**:
```markdown
## 对方角色上下文
- 角色名：${charName}
- 角色个性：${personality}      // 润色任务不需要，触发角色扮演
- 角色描述：${characterCardContent}  // 润色任务不需要，触发角色扮演
```

**正模式**:
```markdown
## 角色名（仅作润色参考，不要扮演这个角色）
${charName}
```

**检查清单**:
- [ ] 每个注入的字段是否与任务直接相关？
- [ ] 是否在上下文段落标题中明确标注"仅作参考，不要扮演/续写/回答"？
- [ ] 角色个性、角色描述等"扮演触发器"字段是否真的需要？如果只是为了润色结果能正确使用角色名，仅注入角色名即可。

#### 规范 5：消息结构与系统提示的协同

`engine.sendMessage(messages, systemPrompt, config)` 的 `messages` 数组结构与 `systemPrompt` 的内容必须协同设计：

- **对话历史以 assistant 结尾** → LLM 倾向续写对话（生成下一条 assistant 回复）
- **对话历史以 user 结尾** → LLM 倾向回答问题（生成对 user 的回复）
- **messages 数组仅含 [system, user(任务请求)]** → LLM 执行 user 消息中明确请求的任务

当任务不是"对话续写"时，**不要把对话历史作为 messages 数组传给 engine**，而应将对话历史格式化为文本嵌入系统提示，让 messages 数组只含 [system, user(任务请求)]。

**检查清单**:
- [ ] messages 数组的最后一条消息角色是否符合任务期望（润色任务应以 user 结尾而非 assistant）？
- [ ] 对话历史是否真的需要作为 messages 数组传递？还是可以嵌入系统提示？
- [ ] 系统提示中的约束是否能在 messages 数组结构下生效？（弱约束无法对抗强消息结构）

### 2.2 顽固 Bug 诊断规范

**适用场景**: 用户报告的 bug 经第一轮修复后无效，或同一问题反复出现 2 次以上。

#### 规范 6：多轮修复无效时的根因深挖

当第一轮修复无效时，**不要在同一个层面继续修复**。必须升级诊断层面：

| 轮次 | 诊断层面 | 典型问题 |
|---|---|---|
| 第 1 轮 | 提示措辞层面 | "约束写得不够明确" |
| 第 2 轮 | 提示结构层面 | "段落顺序不对" |
| 第 3 轮 | 消息结构层面 | "messages 数组以 assistant 结尾触发续写" |
| 第 4 轮 | 任务框架层面 | "系统提示残留对话生成语义触发词" |
| 第 5 轮 | 模型行为层面 | "需要 response_format 强制 JSON / few-shot 示例" |

**反模式**: 在第 1 轮的层面反复修复 3 次以上（如反复改提示措辞），不升级诊断层面。

**检查清单**:
- [ ] 当前修复是否在同一层面打转？是否需要升级层面？
- [ ] 是否对比了"正常工作的孪生函数"与"失败的函数"的差异？
- [ ] 是否实际打印了发送给 LLM 的完整 messages 数组与 systemPrompt？（而非凭代码推断）
- [ ] 是否检查了 LLM 返回的完整内容？（而非只看前端渲染后的内容）

#### 规范 7：孪生函数对比诊断法

当某个功能失败但其孪生功能正常时，**对比两者的差异是定位根因的最快手段**。具体步骤：

1. 找到孪生函数（如 `buildPolishInputSystemPrompt` 的孪生是 `buildUserReplySystemPrompt`）
2. 逐段对比两者的系统提示输出（开头任务定义、段落结构、personConstraint、任务要求）
3. 找出"失败的函数"与"正常的孪生函数"中**完全相同**的措辞——这些是嫌疑对象
4. 分析这些措辞在"正常的孪生函数"上下文中是否合理（如"生成回复"在生成回复函数中合理）
5. 分析这些措辞在"失败的函数"上下文中是否合理（如"生成回复"在润色函数中错误）
6. 修改失败的函数，使措辞与任务类型匹配

**检查清单**:
- [ ] 是否找到了孪生函数？
- [ ] 是否逐段对比了输出？
- [ ] 是否分析了共用的措辞在两个上下文中的合理性？

### BUG-001: 润色功能 AI 误判为对话生成任务（fix-polish-task-framing）

| 字段 | 内容 |
|---|---|
| 问题 ID | BUG-001 |
| 发现日期 | 2026-07-05 |
| 修复日期 | 2026-07-06 |
| 修复轮次 | 第 4 轮（共 4 轮，前 3 轮无效） |
| 影响范围 | 角色对话聊天模块的"润色输入"功能（`polishInput`）；用户在输入框输入草稿文本后点击润色按钮，AI 应输出润色扩展后的文本，但实际输出对草稿的直接回复 |
| 严重级别 | High（功能完全不可用，但仅影响润色功能，不影响主对话流程） |
| 相关 Spec | `fix-polish-input-undo-and-target`（阶段六） / `fix-polish-target-misinterpretation`（阶段七） / `fix-polish-context-isolation`（阶段八） / `fix-polish-task-framing`（阶段九，最终修复） |
| 相关文件 | `src/renderer/components/Character/CharacterDialogueChat/PromptBuilder.ts`、`src/renderer/components/Character/CharacterDialogueChat/CharacterDialogueChat.hooks.ts`、`src/renderer/components/Character/CharacterDialogueChat/__tests__/PromptBuilder.polishInput.test.ts`、`doc/04b-character-dialogue-chat-module.md` |

#### 1. 问题现象

**触发条件**: 用户在角色对话聊天界面的输入框中输入草稿文本（如"你吃饭了吗"），点击"润色"按钮。

**期望行为**: AI 输出润色扩展后的文本（如"你今天早上吃饭了吗？在哪里吃的？"），填入输入框供用户编辑后发送。

**实际行为**: AI 输出对草稿的直接回复（如"我吃过了"），将待润色的问句当作"需要回答的问题"处理。

**复现步骤**:
1. 进入角色对话聊天界面
2. 在输入框输入"你吃饭了吗"
3. 点击"润色"按钮
4. 观察 AI 返回内容——返回"我吃过了"而非"你今天早上吃饭了吗？在哪里吃的？"

#### 2. 根本原因分析

**前几轮修复（无效）**:

- **第 1 轮（阶段六 `fix-polish-input-undo-and-target`）**：
  - 诊断：润色目标错误定位到最后一条 AI 回复（而非用户输入框草稿）
  - 修复方案：向 `contextMessages` 末尾追加合成 user 消息 `{role: 'user', content: originalText}` 锚定润色对象
  - 为何无效：合成 user 消息让 AI 把 originalText 当作"用户提问"来回答，产生新问题（AI 直接回答而非润色）

- **第 2 轮（阶段七 `fix-polish-target-misinterpretation`）**：
  - 诊断：合成 user 消息导致 AI 把润色对象当作问题回答
  - 修复方案：移除合成 user 消息 + 用 `<polish_target>` 标签包裹 originalText + 新增"关键约束"段落
  - 为何无效：仅在"提示措辞层面"修复，没有意识到根因在更深的层面。`<polish_target>` 标签和弱否定约束（"不是需要回答的问题"）无法对抗对话历史的强模式上下文

- **第 3 轮（阶段八 `fix-polish-context-isolation`）**：
  - 诊断：对话历史以 assistant 结尾触发 AI 续写本能（消息结构问题）
  - 修复方案：将对话历史从 `engine.sendMessage` 的 `contextMessages` 参数中移除，改为嵌入 `polishSystemPrompt` 作为"## 对话历史参考"段落；`engine.sendMessage` 接收单条 user 润色请求消息
  - 为何无效：改变了消息结构（[system, user] 替代 [system, ...对话历史]]），但**没有消除系统提示中残留的对话生成语义触发词**。AI 看到 system prompt 中的"生成回复"措辞和"确保上下文连贯"指令，仍走对话生成路径

**最终诊断（第 4 轮，`fix-polish-task-framing`）**:

通过对比 `buildPolishInputSystemPrompt`（润色，失败）与孪生函数 `buildUserReplySystemPrompt`（生成用户回复，正常工作），定位到 4 个对话生成语义触发器：

1. **personConstraint 措辞错误（最关键）**：`buildPolishInputSystemPrompt` 第 7 条任务要求使用 `以第一人称（"我"）视角生成回复，使用"我"作为自称`，与 `buildUserReplySystemPrompt` 中的 personConstraint **完全相同**。"生成回复"是核心误导词——AI 看到这个词会优先走对话生成路径。
2. **任务要求第 6 条是对话生成指令**：`结合对话历史参考与 ${charName} 的最新发言确保上下文连贯` 让 AI 把"润色"理解为"基于上下文生成下一句连贯回复"。
3. **关键约束出现在待润色文本之后**：AI 在读到 `<polish_target>` 之前，已经从"## 对方角色上下文"（含 personality / characterCardContent）和"## 对话历史参考"段落构建出"我正在和 CharName 对话"的认知。`<polish_target>` 内的问句自然被当作"用户在对话中提的问题"，而关键约束（出现在 polish_target 之后）的约束力已被稀释。
4. **"## 对方角色上下文"段落过重**：包含 `personality` 和 `characterCardContent`，这些是角色扮演触发器，让 AI 进入"扮演这个角色回复"模式。

**前几轮诊断没看到这一层的原因**：前 3 轮诊断停留在"消息结构"和"提示措辞"层面，没有对比孪生函数的措辞差异。第 4 轮通过孪生函数对比法，才发现 personConstraint 措辞在两个函数中完全相同，但仅在润色函数中是错误的（"生成回复"对生成回复函数合理，对润色函数错误）。

#### 3. 修复方案

**核心思路**: 从任务框架（Task Framing）层面入手，彻底去除系统提示中的对话生成语义信号。让润色函数的系统提示从开头到末尾，每一个字都在强化"这是文本润色任务，不是对话生成任务"。

**改动点**（仅在 `buildPolishInputSystemPrompt` 函数内重构，不动 `polishInput` 调用结构）:

1. **强化开头任务定义**：从"你是文本润色器，需要基于对话上下文优化..."改为"你是文本润色器，需要优化...**禁止生成对话回复，禁止回答 <polish_target> 内的任何问题**，仅对原文进行润色扩展后输出。"
2. **精简角色上下文**：删除 personality 和 characterCardContent 注入；"## 对方角色上下文"段落改为"## 角色名（仅作润色参考，不要扮演这个角色）"，内容仅为 `${charName}`
3. **调整段落顺序**："## 关键约束"段落提前到"## 待润色文本"之前
4. **强化关键约束措辞**：从"不是需要回答的问题"（弱否定）改为"**绝对禁止**回答..."、"**绝对禁止**生成对话回复"（强禁止）
5. **修改任务要求第 6 条**：从"结合对话历史参考与 ${charName} 的最新发言确保上下文连贯"（对话生成指令）改为"润色结果需与对话历史不矛盾即可，**无需衔接角色发言，无需推进对话**"（反对话生成）
6. **修改 personConstraint 措辞**：从"以第一人称视角**生成回复**"改为"润色后的文本以第一人称视角**输出**"
7. **更新 JSDoc 注释**：标注 `Spec: fix-polish-task-framing`

**与失败方案的对比**:

| 维度 | 阶段八方案（失败） | 阶段九方案（最终） |
|---|---|---|
| 任务定义 | "你是文本润色器，需要基于对话上下文优化..." | "你是文本润色器...**禁止生成对话回复，禁止回答 <polish_target> 内的任何问题**" |
| 角色上下文 | 完整 personality + characterCardContent（角色扮演触发器） | 仅角色名（无扮演触发） |

| 任务要求第 6 条 | "结合对话历史参考与 ${charName} 的最新发言确保上下文连贯"（对话生成指令） | "润色结果需与对话历史不矛盾即可，无需衔接角色发言，无需推进对话"（反对话生成） |

#### 7. 经验教训

**关键教训**:

1. **孪生函数对比是最快的诊断手段**：当某个功能失败但其孪生功能正常时，对比两者的措辞差异是定位根因的最快手段。前 3 轮修复没有对比孪生函数，导致在错误层面打转。第 4 轮通过对比 `buildPolishInputSystemPrompt` 与 `buildUserReplySystemPrompt`，立即发现 personConstraint 措辞完全相同但仅在润色函数中错误。

2. **多轮修复无效时必须升级诊断层面**：第 1-2 轮在"提示措辞层面"修复，第 3 轮升级到"消息结构层面"，第 4 轮升级到"任务框架层面"。如果在第 2 轮无效后就升级到任务框架层面，可以节省 2 轮迭代。

3. **任务框架（Task Framing）是 LLM 行为的主导因素**：LLM 的行为主要由"任务类型"决定，而任务类型由系统提示中的"任务定义层"（开头第一句话）和"任务要求层"（每一条要求）共同确定。如果系统提示中残留其他任务类型的语义触发词（如润色任务中的"生成回复"），LLM 会优先走该任务类型的路径，无视任何约束。

4. **关键约束的位置与强度决定约束力**：弱否定（"不要"）+ 后置（待处理对象之后）= 几乎无约束力。强禁止（"**绝对禁止**"）+ 前置（待处理对象之前）= 约束力最大化。

5. **上下文注入应最小化**：多余的上下文（如角色个性、角色描述）可能触发 LLM 进入"角色扮演"模式，与任务定义冲突。润色任务只需要角色名（供润色结果正确使用），不需要角色个性/描述。

6. **消息结构与系统提示必须协同**：阶段八解决了消息结构问题（[system, user] 替代 [system, ...对话历史]），但单独解决消息结构不够，还需要解决系统提示语义问题（去除对话生成关键词）。两者叠加才能彻底切断 LLM 走对话生成路径。

7. **顽固 bug 的修复必须文档化**：用户报告的顽固 bug（反复修复无效）必须按标准化模板文档化，记录每一轮诊断与失败原因，便于团队成员学习与避免同类问题。

**预防措施**: 见本文件第二部分"编码规范 / 检查清单"，特别是：
- 规范 1：任务框架（Task Framing）一致性
- 规范 2：孪生函数差异化
